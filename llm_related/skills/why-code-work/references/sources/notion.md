# Notion 文件

## 這個來源裡有什麼

- PRD（產品需求文件）
- 技術規格和 RFC
- 架構決策記錄（ADR）
- 設計評審的會議紀要
- 帶領域上下文的團隊頁面
- 事故的事後覆盤
- 可能解釋防禦性程式碼的 runbook
- 定下優先順序的戰略文件

「為什麼」常常先在 Notion 裡寫成長文，然後才變成程式碼。一個重要功能通常會有一份文件。

## 怎麼搜

使用 Notion MCP。

1. **用 `notion-search` 做關鍵詞搜尋。** 可以試：
   - 功能名
   - 目的碼裡的關鍵符號 / 類名
   - 作者的 handle（設計文件常常在程式碼落地之前就寫好了）
   - 錯誤字串，或使用者能看見的詞
   - 如果知道程式碼什麼時候上線，把查詢限在那段時間
2. **用 `notion-fetch` 把候選頁拉下來。** 讀全文，不要只看預覽。理由常常埋在文件中部。
3. **跟著反向連結和子頁走。** 設計文件常常有子頁，用來寫考慮過的替代方案、附錄或實現筆記。
4. **查相關資料庫。** `notion-query-data-sources` 和 `notion-query-meeting-notes` 能翻出討論過這個決定的會議紀要。
5. **搜作者自己的空間。** 如果 PR 作者有個人筆記空間（有些公司裡很常見），裡面可能有先於程式碼的探索。

## 怎樣算好證據

- 一份 PRD，裡面的 "Problem statement"（問題陳述）或 "Motivation"（動機）對得上目的碼在幹什麼
- 有 "Alternatives considered"（考慮過的替代方案）或 "Rejected approaches"（沒采納的做法）
- 一份事後覆盤，點名目的碼是某次事故的修復
- 會議紀要裡寫著「我們決定 X，因為 Y」，作者和時間範圍又和這條 PR 對得上
- ADR 模板填得不敷衍（status、context、decision、consequences 都有實打實的內容）

## 常見陷阱

- **文件過時。** 規格常常在實現之前寫完，之後不再更新。文件描述的，可能是後來已經改掉的方案。拿實際的 PR 對一下。
- **文件和現實分開了。** 規格寫「我們會做 X」，程式碼實際做的是 Y。把這個分歧標出來。合成器會把矛盾擺出來。
- **模板空話。** 有些組織要求填 "Why" 一節，裡面常常是空話。要找具體的內容。
- **沒有入鏈的文件。** 最相關的那份，可能沒有任何連結指向它。把關鍵詞搜寬一點有用。
- **好幾份草稿。** 同一個題目有多份文件時，找定稿的，或最近更新的。看日期。
- **打不開的頁面。** 某一頁訪問不了，就把它記成缺口。

## 要返回什麼

每份相關文件：

- 標題和 URL
- 作者，以及最後更新日期
- 動機原文（逐字引用），並寫明在哪一頁、哪一節
- 相關的連結頁（方便合成器引用）
- 這份文件是定稿還是草稿
