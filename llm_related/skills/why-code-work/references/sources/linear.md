# Linear 工單

## 這個來源裡有什麼

- 描述功能、bug 及其動機的 issue
- 附在 issue 上的專案文件（常常是 PRD 或規格）
- 父 / 子 issue 的關係（從更大的計劃到具體工單）
- issue 上的評論（澄清、範圍變更、「我們為什麼做這個」的理由）
- 標籤（例如 `compliance`、`customer-request`、`perf`），標出動機屬於哪一類
- 解釋範圍為什麼變了的狀態更新
- 附件，以及連結到的 GitHub PR

Linear 裡常常有產品 / 業務這一層：「因為客戶 X 提了要求」，或者「這是為了 Q3 的合規計劃」。

## 怎麼搜

使用 Linear MCP。

1. **從已經關聯上的工單開始。** 種子提交或 PR 如果提到工單 ID（例如 `ENG-1234`、`[BUG-567]`），先用 `get_issue` 把它們拉下來。整張工單連評論一起讀。
2. **按關鍵詞列相關工單。** 用 `list_issues` 做文字搜尋，搜功能名、關鍵符號或業務詞。多換幾種說法。
3. **順著工單樹走。** 如果落在子工單上，把父工單拉下來。子工單是戰術層面的，父工單常常帶著「為什麼」。
4. **讀專案文件。** 工單如果屬於某個專案，用 `get_project` 看附上的文件。規格和理由最常寫在專案級文件裡。
5. **看標籤和里程碑。** 標籤暗示動機屬於哪一類（customer-request、incident-followup、compliance）。里程碑把工作和截止日期綁在一起，截止日期常常露出動機。

## 怎樣算好證據

- 工單描述寫明瞭業務問題：「客戶 Acme 因為 SOC2 審計需要 X」
- 一條評論記下了決定：「我們選方案 B，因為方案 A 得去動計費服務」
- 父工單的標題像一項計劃："Q3 Enterprise Readiness" 或 "Reduce Payment Failures"
- 附了一份 PRD 或規格
- 標籤如 `customer:acme`、`incident-followup`、`compliance`、`perf-regression`

## 常見陷阱

- **範圍漂了。** PR 引用的那張工單，可能已經關掉，又以另一個範圍重開。把整段歷史讀完。
- **套模板。** 有些團隊要求填 "Why"，但填的是套話。泛泛的一句（"improve user experience"，提升使用者體驗）多半不是真答案。
- **過期工單。** 舊工單常常還停在後來已經改過的方案上。對一下日期，再和程式碼實際上線的日期交叉看。
- **以 duplicate 關掉的鏈。** 順著 duplicate-of 關係追回那張真正的主工單。
- **私有工作區。** 某張工單打不開，就記成缺口，不要猜。

## 要返回什麼

每個相關工單：

- 工單 ID 和標題
- 從描述或評論裡引來的問題 / 動機（不要意譯。合成器要拿原文去引用）
- 標籤、父工單、專案
- 作者、建立日期、關閉日期
- 有連結就附上
