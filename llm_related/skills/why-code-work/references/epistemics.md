# 認識論

證據是歷史留下的、零散的，有時還互相矛盾。這時要判斷自己有多把握，並且告訴使用者，不要把它壓成虛假的確定性。程式碼顯示它做什麼，不顯示*它為何存在*。原因在提交、PR、工單、文件和對話裡。這些材料都不完整，有偏見，有時根本沒有。假裝它們可靠，就會寫出聽起來很有把握、實際會誤導使用者的猜測。

## 置信度層級

輸出裡的每條主張都必須落在一個層級裡。層級決定它進哪一節，以及怎麼措辭。

### 1. 直接

有明確的文字引用，而且它回答了問題：作者實際*寫下*的原因，不是「程式碼做了 X，所以作者一定想要 X」。例如：PR 描述寫「修復了使用者超過 1000 條時無法分頁的 bug」；工單寫「客戶 Acme 在安全審查裡提出了要求，所以我們加上這個」；程式碼註釋寫 "// clamp to 100 because the upstream API rejects larger values"（把上限鉗在 100，因為上游 API 會拒絕更大的值）；設計文件寫「選 A 不選 B，因為重啟之後還得留得住」；作者的聊天寫「改用這個做法，舊的那個在測試裡時好時壞」。

措辭：有把握，用現在時，並註明出處。「它之所以存在，是因為 X。」

### 2. 有支撐

多條間接證據收斂到同一個結論。沒有單一來源明說，但跨來源的模式讓它很可能成立。例如：PR 標題寫「提升效能」，工單標了 perf，周圍的提交都改到同一條熱路徑。或者這次變更加上的好幾條測試，跑的都是非常大的輸入。或者作者同一周的其他 PR，都點名了同一起事故。

措辭：有把握，但明顯是推匯出來的，並逐條引用。「證據強烈指向 X：[具體是哪幾條]。」

### 3. 推斷

對上下文的一種合理解讀，沒有明文支援。這是*你的解釋*，不是記錄裡的事實。例如：PR 沒寫原因，但生產當時在報錯（按事故頻道的時間），修復又很趕（當天就合併了），所以多半是一次熱修復。或者函式名像重試邏輯，重試次數是 3，和程式碼庫別處「重試 3 次」的慣例一致。

措辭：留有餘地，並把推斷鏈寫明。「鑑於 A 和 B，C 很可能成立，因為 D。」

### 4. 推測

說得通的假設，證據很薄，別的解釋也同樣說得通。值得寫出來，使用者可能知道哪個對，但要標明這是猜測。例如：「這可能是在繞某個後來已經修好的瀏覽器 bug，但我們沒找到當時的證據。」或者：「這個閾值可能是為了對齊某份 SLA，但沒有 SLA 文件提到它。」

措辭：「一種可能是 X，但我們沒有直接證據。」通常放在競爭假設裡，和其他可能並列。

### 5. 未知

你查過了，還是不知道。這是有效而且重要的結果。把它記下來。

措辭：「我們搜了 X、Y、Z，沒找到原因的證據。」要具體寫出*搜了什麼*。「我們查不到」不如這句有用：「我們在工單跟蹤裡用關鍵詞 A 和 B 搜過，掃了 2023 年以來改過這個檔案的 6 個 PR，又在倉庫裡 grep 和這個閾值匹配的字串字面量。都沒有翻出寫明的理由。」

## 措辭指南

**表示確信的詞**意味著證據是直接或有支撐的，旁邊必須立刻有引用。推斷裡**絕不**用這些詞：「因為」、「原因是」、「當初就是為了」（這是在聲稱作者的意圖）、「修復了」/「應對了」/「解決了」（這是在聲稱這次改動達成了目標）、「團隊決定」（這是在聲稱發生過群體決策）。

**留有餘地的詞**表示你在解釋，不是在轉述記錄。在「可以合理推斷的」裡可以多用：「看起來」、「似乎」、「很可能」、「表明」、「與……一致」、「一種解讀是」、「說得通」、「可能曾是」、「證據指向」。

**避免使用的詞：**

- 「顯然」。如果真的顯然，使用者不會來問
- 「很明顯」。幾乎總是出現在並不明顯的主張前面
- 「當然」。同上
- 「只是」（比如「這只是為了效能」）。帶著輕視，而且通常藏著不確定
- 「我認為」/「我相信」。你在綜合證據，不是在給個人意見。改說「證據表明」

## 避免合理化

今天「說得通」的程式碼，寫它的理由可能已經不適用，或者當時就不對。不要給亂的歷史補一套乾淨的理由。不要假設作者做了「對」的事，再倒推著替它辯護。不要假設前後一致的模式是有意的，它可能只是複製貼上。不要把沒有證據，當成這件事不存在的證據（「沒人提過安全方面的顧慮，所以當時一定不在意」）。

## 附和陷阱

使用者常把假設嵌在問題裡："Why do we do it this way, I assume it's for performance?"（我們為什麼這樣做？我猜是為了效能）。不要直接順著確認。這個猜測是調查的起點，不是待驗證的結論。把它當作候選之一，獨立去查證據。證據支援，就帶引用說明。不支援，也說明，並寫出證據*實際*支援什麼。

## 證據互相矛盾時

兩條來源都寫進輸出，並附上引用。不要挑那個更整齊的故事。例如工單說「客戶 X 的合規要求需要這個」，PR 說「清理這塊的技術債」。兩條都可能是真的（工單推動了這項工作，PR 寫出的是作者自己的說法），也可能有一條是錯的。交給使用者判斷。

## 證據缺失時

誠實的「我們不知道」是最有價值的輸出之一。使用者會由此知道：答案不在顯眼的地方；得去問人（原作者、產品負責人、團隊負責人）；或者可以決定這個問題不值得再追。不標出缺口，反而用聽起來有把握的猜測填上，會害到使用者，因為他們會照著猜測行動。每個缺口都要具體寫出：問題是什麼，搜了哪些來源，每個來源裡搜了什麼，找到了什麼（沒有，或只有沾邊的材料）。

## 定稿前

合成器交稿之前，檢查「已經查到的」和「可以合理推斷的」裡的每一條主張。每條要麼有引用，要麼挪到「可以合理推斷的」或「競爭假設」。措辭要和它的層級匹配。不要把程式碼當成它自身意圖的證據。如果這樣做了，刪掉，或改到別的層級。輸出裡要有「還不知道的」一節。完全沒提缺口的話，要起疑。要麼證據難得這麼全，要麼漏寫了缺口。
