# Why

調查程式碼背後的動機和意圖。配套的 `how-code-work` skill 回答程式碼做什麼、怎麼工作；`why-code-work` 回答是哪些力量把它變成了現在的樣子。

以下 `references/...` 路徑都相對於本 `SKILL.md` 所在目錄。

## 派生子代理

用 `subagent` 工具，**不要指定 `model`**，一律沿用目前對話的模型。

- **調查員**和**合成器**都用 `agent: "general"`。不用 `explore`；那個是唯讀快速探查，擔不起證據調查。
- 提示詞裡明確寫「只讀，不要修改、建立或刪除任何檔案」。調查員本來就不該寫任何東西。
- 要並行的調查員放在同一則訊息裡一起送出。全部回來才進合成。

## 工作姿態

像一名**謹慎、保守、精確的調查者**那樣工作，把已知和推斷誠實分開。完整的置信度框架和措辭指南在 `references/epistemics.md`，合成器**必須**照著它。

## 第 1 步：弄清目標與問題

**目標**通常是一塊程式碼、一種模式、一個功能，或一項有名字的設計決策。**問題**通常是設計理由、一處權衡、逼出某個邊界情況的原因、一項外部約束、死程式碼，或一次寬泛的歷史梳理。

目標含糊時，比如 "why do we do it this way?"（我們為什麼這樣做？）又沒有明確指代，就根據對話上下文做最好的猜測（開啟的檔案、最近的編輯、剛聊過的內容）。用一兩句說出你的理解，方便使用者在你偏了的時候糾正，然後繼續。

## 第 2 步：立住程式碼錨點

派出調查員前先自己把種子上下文備好：檔案路徑和行範圍、關鍵符號（函式、類、常量）、最近碰過該目標的幾次提交、合併提交主題行裡的 PR 編號（`(#1234)` 這種模式），以及任何關聯的工單 ID。用 `git blame -L <start>,<end> <file>` 查最後改這些行的提交，用 `git log --follow -p -- <file>` 看跟蹤重新命名的完整歷史和補丁，用 `git log --oneline -20 -- <file>` 看最近提交和裡面的 PR 編號，用 `git log -1 --format=%B <commit>` 抽出 PR 編號。然後對有實質內容的提交，用 `gh pr view <number> --json title,body,author,createdAt,mergedAt,labels,closingIssuesReferences,comments,reviews` 把 PR 正文和討論拉下來。這份錨點交給每個調查員，也交給合成器。

`gh` 失敗時（私有 repo 沒授權、不是 GitHub、沒登入）降級成純 git：`git log`、`git blame`、程式碼註釋、測試。記下失敗原因，第 5 步的「已查閱來源」要寫明。不要因此中止調查。

## 第 3 步：並行派出調查員

**預設做完整的並行調查。** 要的是一張完整的覆蓋圖，不要為了省事縮成最小的一張。空結果要記下來，不要跳過搜尋。

### 清點

派出調查員前先列出可用的 MCP。看目前生效的 OpenCode 設定（`opencode.jsonc` / `opencode.json`，含專案層 `.opencode/`）裡的 `mcp` 區塊，只算沒有 `"enabled": false` 的伺服器；需要時再用 `opencode.list_mcp_resources` 看它暴露了什麼。`read`、`grep`、`glob`、`shell` 這些內建工具不算 MCP。

把每個可用 MCP 歸到一個證據類別：

1. 原始碼控制歷史
2. 工單 / ticket 跟蹤
3. 長文文件
4. 實時團隊聊天
5. 基礎設施可觀測性
6. 錯誤 / 異常跟蹤
7. 產品分析數倉

原始碼控制始終可用，走 git 和 `gh`。其餘六類，看 MCP 名字、伺服器說明、工具名和資源描述來歸類。一個 MCP 能歸進好幾類時，按它主要的證據來歸類。拿不準的記進覆蓋圖。

每個有匹配 MCP 的類別派一名調查員，放在同一條訊息裡一起跑。每人只負責一個工具或一個 MCP。不要讓一個代理同時覆蓋多個 MCP。

每個調查員的提示詞是填好的 `references/investigator-prompt.md`，再加上下面這些：

- 所選 MCP 的類別 playbook `references/sources/<source>.md`，按 `references/source-playbook.md` 裡的例子改寫
- `references/sources/incident-postmortem.md`，**如果目的碼看起來是防禦性的**（空值檢查、重試、超時處理、限流、功能開關、出口守衛、OOM 處理）
- 程式碼錨點，以及使用者原來的問題

### 調查員名冊：每個有證據的類別一名

下面每一類都能翻出一種別的來源給不了的「為什麼」，寫在「最擅長」後面。用它來判斷該等回什麼、某一類空著時怎麼稱呼這個缺口，並且在極少數能證明無關時，說明為什麼跳過。

1. **原始碼控制**（git 歷史、用 `gh` 查 PR、程式碼註釋、測試）。始終要派，這是唯一保證有的來源。最擅長*評審當時記下來的實現理由*。
2. **工單 / ticket 跟蹤**（如 Linear、Jira、GitHub Issues、Plane、Shortcut MCP）。最擅長*產品或業務層面的推動力*。當「為什麼」落在工程之外時最強。
3. **長文文件**（如 Notion、Confluence、Google Docs、Coda MCP）。最擅長*落成文字的設計理由*，在變成程式碼之前就寫下來的那種。
4. **實時團隊聊天**（如 Slack、Discord、Microsoft Teams、Mattermost MCP）。最擅長*沒寫進文件的即時討論*。原始碼控制、工單和文件幾乎沒留下書面記錄時，這一類尤其重要。
5. **基礎設施可觀測性**（如 Datadog、New Relic、Honeycomb、Grafana、Splunk MCP）。最擅長*促使寫下這段程式碼的基礎設施和執行時事實*。當目標是在響應基礎設施訊號（超時、重試、限流、熔斷）時，這一類最強。
6. **錯誤 / 異常跟蹤**（如 Sentry、Rollbar、Bugsnag、Airbrake MCP）。最擅長*促使寫下防禦或糾正程式碼的具體異常和錯誤軌跡*。對 catch 塊、空值守衛、型別檢查、重試和其他防禦程式碼最強。
7. **產品分析數倉**（如 Databricks、Snowflake、BigQuery、ClickHouse、dbt、Redshift MCP）。最擅長*塑造這段程式碼的產品和資料事實*。對掛在功能開關後面的程式碼、實驗驅動的釋出、資料遷移，以及 "where did this number come from"（這個數字從哪來）這類問題最強。

### 什麼時候可以跳過一名調查員

只有**寫明的理由**才能跳過，理由要寫進最終的已查閱來源。兩種站得住腳的理由：

- **這一類在本環境沒有可用的 MCP**。標成缺口，不是你的選擇：「實時團隊聊天已跳過。沒有匹配的 MCP，對話記錄搜不了。」
- **來源可以證明確實無關**，不是「大概不相關」。門檻很高：「錯誤 / 異常跟蹤已跳過。目標是構建期指令碼，沒有執行時路徑。」

如果你判斷這是單次提交的瑣碎目標，而且 PR 描述裡已經有完整答案，可以在當前執行緒直接回答，**但只有確認七類裡每一個能用的搜尋都是重複勞動之後才行**。把這一點寫明。這種情況應該很少。

## 第 4 步：合成

派一名合成器。它拿到：

1. 調查員的發現，包括空結果，以及寫明理由後跳過的類別
2. 程式碼錨點
3. 使用者原來的問題
4. `references/epistemics.md` 的**全文**，貼進 `references/synthesizer-prompt.md` 的 `{EPISTEMICS_FULL_TEXT}` 佔位符
5. `references/synthesizer-prompt.md` 的其餘內容，佔位符填滿

## 第 5 步：交給使用者

把合成器的輸出交給使用者。為了更清楚，或為了補上對話裡的上下文，可以小改，但**不要改寫置信度措辭**。

## 輸出格式

結構以 `references/synthesizer-prompt.md` 為準：問題、相關程式碼、已經查到的、可以合理推斷的、競爭假設、還不知道的、已查閱來源、置信度摘要。可以按需要調整，但置信度的分層要保住。已查閱來源每個調查員一行，包括沒有結果的和跳過的，都要寫上理由。

已查閱來源之後，如果使用者的 `why` 問題是為了接著改這段程式碼，把這條程式碼的來歷收成一套 Preserve / Change / Avoid / Risk（保留 / 改 / 避開 / 風險）約束，用來規劃這次改動。

## 要避開的常見失敗

- **近因偏誤**。別把最近一次提交當成權威。現在的樣子，往往是更早一連串決定疊加出來的，要往回追。
